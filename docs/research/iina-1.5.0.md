# IINA 1.5.0 plugin facts

Checked on 2026-10-20. This records feasibility evidence, not accepted product or architecture decisions. Runtime details below use upstream's `v1.5.0` tag. The public API documentation is unversioned and contains some stale examples.

## Release and local availability

The official release page marks IINA 1.5.0 as the latest release. It includes a plugin store in Settings and bundles mpv 0.41.0 and FFmpeg 9.0.1. The plugin system was already enabled by default in the 1.4.0 release series. [1.5.0 release](https://github.com/iina/iina/releases/tag/v1.5.0), [1.4.0 beta release](https://github.com/iina/iina/releases/tag/v1.4.0-beta1)

Read-only inspection of `/Applications/IINA.app/Contents/Info.plist` found version `1.5.0`, build `180`. IINA is available locally; this check did not launch it, install a plugin, exercise playback, or access an account.

```sh
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' /Applications/IINA.app/Contents/Info.plist
/usr/libexec/PlistBuddy -c 'Print :CFBundleVersion' /Applications/IINA.app/Contents/Info.plist
```

## JavaScript contexts

Host scripts run in JavaScriptCore. They have no browser `window`, `fetch`, or `localStorage`; IINA supplies `iina.http`, timers, and a basic `require`/`module.exports` loader. This loader does not make Node.js modules available. UI scripts execute separately in WebKit, so plain HTML, CSS, and JavaScript fit the host. The documentation's old macOS/ES6 discussion is not a version-specific compatibility promise for 1.5.0. [Development guide](https://docs.iina.io/pages/dev-guide.html), [v1.5.0 loader](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptPolyfill.swift)

Each player gets a separate main plugin instance. A global instance exists once and can operate before any media window opens. Version-pinned API registration confirms these boundaries:

| Operation | Main | Global |
| --- | --- | --- |
| Menu, standalone window, HTTP, files, preferences, utilities | Yes | Yes |
| Player control, mpv, events, sidebar, overlay, playlist | Yes | No |
| Create managed players and address child instances | No | Yes |
| Send messages to the global instance | Yes, when global entry exists | N/A |

[Entry-point guide](https://docs.iina.io/pages/getting-started.html), [v1.5.0 API registration](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptPluginInstance.swift#L130-L175)

The global API can create a player with `createPlayerInstance(options)` and exchange messages with main instances. A managed player loads only this plugin unless `enablePlugins` is true. Its numeric identifier belongs to the global controller. No product choice about reusing a player or creating one is implied here. [v1.5.0 global API](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIGlobal.swift)

## Views and messages

All three views use named messages with JSON-serializable data. Host code uses `standaloneWindow`, `sidebar`, or `overlay` `.onMessage` and `.postMessage`; view code uses `iina.onMessage` and `iina.postMessage`. A view cannot invoke host playback or network APIs directly. Messages between views must pass through host code. [Webview messaging](https://docs.iina.io/pages/webviews.html)

Version-pinned exports use `loadFile(path)` for all three views. The standalone window opens with `open()`. Older prose examples that say `loadHTML()` or `standaloneWindow.show()` should not be copied. Calling `loadFile` clears that view's host message listeners, so register listeners after loading. Sidebar and overlay initialization require `iina.window-loaded`; overlay also requires `video-overlay`. Overlay listener registration requires its view to be loaded, which warrants checking initialization ordering in IINA. [Standalone source](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIStandaloneWindow.swift), [sidebar source](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPISidebarView.swift), [overlay source](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIOverlay.swift)

## Network and playback

`iina.http` supports GET/POST/PUT/PATCH/DELETE with `params`, `headers`, and object-form `data`. It returns promises. The bridge resolves successful HTTP responses and rejects unsuccessful ones. The exposed response has only `statusCode`, `reason`, parsed JSON `data`, and `text`. It exposes no response headers, cookie management, request cancellation, or per-request timeout option. There is no supported browser-session import in this API. Cookie sharing between host HTTP and WebKit or Safari must not be assumed. [v1.5.0 HTTP bridge](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIHttp.swift)

`iina.core.open(url)` opens media in the current main instance. It returns no playback-success promise. Player status, seeking, track handling, and event-driven verification are separate operations. [v1.5.0 core API](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPICore.swift)

Opening HTTP/HTTPS media through the core API requires `network-request` and a matching `allowedDomains` host. IINA's shared URL-opening helper logs the complete URL itself, so plugin log redaction cannot prevent signed playback URLs from entering IINA's logs. Its permission check covers the submitted URL; this is not evidence that mpv's subsequent redirects or HLS requests receive equivalent checks. [v1.5.0 URL-opening helper](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPI.swift#L42-L68)

Allowlist matching supports exact host names, `*`, and `*.example.org`. The wildcard form matches subdomains but does not cover the bare host. CDN and redirect hosts therefore need evidence before finalizing the manifest. [v1.5.0 domain matching](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptPluginInstance.swift#L74-L89)

The mpv bridge restricts commands and properties to a safe list unless the plugin has `file-system`. Its safe properties include `http-header-fields`, `user-agent`, `referrer`, `cookies`, and `network-timeout`. Network headers alone therefore do not require broad filesystem access. Their use and cleanup across media changes still need playback verification. [v1.5.0 mpv bridge](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIMpv.swift), [safe options](https://github.com/iina/iina/blob/v1.5.0/iina/AppData.swift#L258-L261)

## Persistence and authentication constraints

The native utilities export `keychainWrite(service, name, secret)` and `keychainRead(service, name)` with a lowercase `c`. They prefix the service with the plugin identifier, return false on failure, and expose no deletion method. The current API documentation instead spells these methods `keyChainWrite` and `keyChainRead`. Prefer the version-pinned export names and verify them in IINA before relying on saved credentials. Logout needs an explicit treatment of saved secrets because a delete operation is unavailable through this API. [v1.5.0 exports and implementation](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIUtils.swift#L23-L59), [unversioned utilities documentation](https://docs.iina.io/interfaces/IINA.API.Utils#keyChainWrite)

Preferences offer `get`, `set`, and `sync`; `set` changes memory and `sync` writes the plugin's property list. These preferences belong to the plugin object shared by its instances. They are ordinary persisted data, so tokens and passwords should use Keychain instead. The plugin also has `@data/` and `@tmp/` directories. [Preference API](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIPreferences.swift), [persistence implementation](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptPlugin.swift#L501-L527)

## Installation and checks still needed

Users can install a `.iinaplgz` archive or a GitHub repository through IINA. Development uses a `.iinaplugin-dev` symlink under `~/Library/Application Support/com.colliderli.iina/plugins`. The bundled CLI lives at `/Applications/IINA.app/Contents/MacOS/iina-plugin`; `pack <dir>` produces a distributable archive. No build tool is required for a direct vanilla source layout. [Creating plugins](https://docs.iina.io/pages/creating-plugins.html)

Before implementation is considered verified, check the selected Anime365 authentication flow with host HTTP, the exact Keychain exports and read/write behavior, view readiness and message delivery, a real entitled stream in mpv, and the media/CDN domain set. None of those authenticated or runtime behaviors was exercised during this research.

## Native history and Continue watching

IINA does support playback history and resume. Main-instance `core.getHistory()` exposes `name`, `url`, `date`, `progress`, and `duration`. It does not expose Anime365 IDs, stored media title, or history mutation methods. The result is available only through a main instance because the global instance has no `core`. [History export](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPICore.swift#L100-L110)

Native history recording depends on IINA's `recordPlaybackHistory` preference. It stores the opened URL and deduplicates by its mpv MD5. `PlaybackHistory.mpvProgress` reads a watch-later file when decoding saved history. A newly created history record leaves that field unset, and `core.getHistory()` just returns the cached value. It is therefore not a guaranteed live progress source. [History recording](https://github.com/iina/iina/blob/v1.5.0/iina/HistoryController.swift#L87-L101), [history record initialization](https://github.com/iina/iina/blob/v1.5.0/iina/PlaybackHistory.swift#L53-L84)

For network resources, IINA hashes the complete URL including query parameters. Its `ignore-path-in-watch-later-config` handling changes only local-file identity. mpv 0.41.0 also hashes the complete URL. A refreshed signature or CDN URL therefore produces a different watch-later key. The native History window reopens the stored URL directly; it does not know how to renew an Anime365 playback link. [IINA hashing](https://github.com/iina/iina/blob/v1.5.0/iina/Utility.swift#L483-L515), [mpv hashing](https://github.com/mpv-player/mpv/blob/v0.41.0/player/configfiles.c#L194-L222), [History playback action](https://github.com/iina/iina/blob/v1.5.0/iina/HistoryWindowController.swift#L254-L257)

The welcome window's Resume last file card is a separate feature. It checks `recordRecentFiles`, `resumeLastPosition`, and `FileManager.fileExists(lastFile.path)` before showing the saved last URL. It should not be promised as an Anime365 Continue watching list. [Welcome-window eligibility](https://github.com/iina/iina/blob/v1.5.0/iina/InitialWindowController.swift#L282-L300)

IINA maps its Resume last playback position preference to both mpv's `save-position-on-quit` and `resume-playback`, and sets IINA's watch-later directory. mpv stores the position through the `start` member of `watch-later-options`. Saving and restoring are distinct controls. Replacing the current playlist with `loadfile` also saves under mpv 0.41.0 when saving is enabled; moving to the next playlist item does not. [IINA configuration](https://github.com/iina/iina/blob/v1.5.0/iina/MPVController.swift#L358-L362), [mpv resume options](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/options.rst#L951-L1005)

The IINA open path sets `info.currentURL` and its watch-later hash before opening media. `fileStarted` updates them from mpv's original path, and `fileLoaded` adds that URL to history. On stop or shutdown, IINA saves watch-later configuration when saving is enabled and updates its separate last-played URL and position preferences. [Open path](https://github.com/iina/iina/blob/v1.5.0/iina/PlayerCore.swift#L502-L505), [start event](https://github.com/iina/iina/blob/v1.5.0/iina/PlayerCore.swift#L1930-L1947), [history addition](https://github.com/iina/iina/blob/v1.5.0/iina/PlayerCore.swift#L2073-L2091), [position saving](https://github.com/iina/iina/blob/v1.5.0/iina/PlayerCore.swift#L1863-L1878)

### A supported hook can preserve stable native identity

IINA documents `mpv.addHook("on_load", priority, async next => ...)` specifically for resolving a website URL to its actual media URL. The callback sets `stream-open-filename` and calls `next()` after asynchronous work. The 1.5.0 bridge distinguishes an `AsyncFunction` and otherwise continues automatically. An asynchronous callback must call `next()` even when resolution fails. [IINA hook example](https://docs.iina.io/interfaces/IINA.API.MPV#addHook), [1.5.0 hook continuation](https://github.com/iina/iina/blob/v1.5.0/iina/MPVController.swift#L43-L77)

mpv distinguishes the original `path` from `stream-open-filename`, which can redirect loading in `on_load` or `on_load_fail`. This supports a plausible design where a stable Anime365 page URL remains the native history and resume identity while the plugin resolves a fresh signed stream each time. That integration is an inference from the APIs, not a tested result. [mpv hook contract and stream property](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/input.rst#L1711-L1719)

In IINA 1.5.0, `stream-open-filename` is absent from `safeMPVOptions`. Setting it through `iina.mpv.set` therefore requires the broad `file-system` permission. The hook must also validate its resolved media URL itself; the property setter does not call the core URL permission helper. Native history still lacks a guaranteed live progress list, and its welcome card still has the local-file check. [mpv permission gate](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIMpv.swift#L44-L68), [safe property list](https://github.com/iina/iina/blob/v1.5.0/iina/AppData.swift#L213-L268)

The design choice remains open. A stable-page hook may reuse native resume and History reopening, with broader plugin permissions and a required runtime proof. Opening fresh media URLs directly can avoid that permission, but reliable Anime365 Continue watching then needs local logical IDs, saved position, and fresh URL resolution. The research does not justify treating native resume as absent or sufficient for expiring direct URLs.

## Touch ID and saved-credential clearing

The existing vanilla JavaScript host cannot request or require Touch ID for saved credentials. `keychainWrite` accepts only service, account name, and secret. `keychainRead` accepts service and account name. There is no exported biometric policy, `LAContext`, access-control flag, authentication prompt, or deletion method. [1.5.0 utility exports](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIUtils.swift#L23-L59)

IINA's own `KeychainAccess` helper calls `SecItemAdd`, `SecItemUpdate`, and `SecItemCopyMatching`. It supplies no `SecAccessControl`, `userPresence`/biometric flag, `kSecUseAuthenticationContext`, `kSecUseOperationPrompt`, `kSecUseDataProtectionKeychain`, or `kSecAttrSynchronizable`. [Underlying helper](https://github.com/iina/iina/blob/v1.5.0/iina/KeychainAccess.swift#L33-L95)

Apple's TN3137 says macOS `SecItem` defaults to the file-based keychain unless the data-protection or synchronization flag is true. Biometric protection requires the data-protection keychain. IINA's helper therefore uses the traditional macOS keychain and its ACL rules. A system unlock or access-authorization prompt may appear, depending on the user's keychain state and access rules; the plugin cannot select Touch ID or promise that such a prompt will appear. [macOS keychain implementations and defaults](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)

Apple implements protected retrieval with a `SecAccessControl` policy and, optionally, `LAContext`. These native mechanisms are absent from the IINA export. Calling the existing host APIs preserves the vanilla-only architecture; adding biometric gating would require an IINA host change or a native helper outside that scope. [Apple's biometric Keychain example](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)

HTML login fields can declare `autocomplete="username"` and `autocomplete="current-password"`. Apple documents these as AutoFill hints. They do not expose a Touch ID API or associate a local plugin page with Anime365 passwords. IINA loads its standalone plugin HTML using a local file URL, and its webview setup exports only the plugin messaging bridge. No supported native Password AutoFill integration for that local IINA form was established by this research. Keep any password-manager assistance a runtime experiment, with no promised Touch ID behavior. [HTML AutoFill hints](https://developer.apple.com/documentation/security/enabling-password-autofill-on-an-html-input-element), [IINA local page loading](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIStandaloneWindow.swift#L59-L66), [webview setup](https://github.com/iina/iina/blob/v1.5.0/iina/PluginStandaloneWindow.swift#L34-L53)

The source accepts an empty secret. For an existing readable record, the write path converts `""` to UTF-8 data and updates its value through `SecItemUpdate`. Clearing by overwrite is therefore supported by the code, subject to OS success. Verify both a successful write result and an exact empty-string readback; a `false` read also covers access errors and does not prove that a secret was cleared. An empty record remains, because deletion is unavailable. The update query matches service and class without an account filter, so keep one record per service, or give distinct records distinct services. No Keychain mutation or empty-value runtime test was performed here. [Write/update and read behavior](https://github.com/iina/iina/blob/v1.5.0/iina/KeychainAccess.swift#L33-L95)

## Exact implementation calls and completion detection

The `v1.5.0` tag resolves to commit `fbcff4df7183b335880396af0655f6bb89d46442`. Its controller accepts `global.createPlayerInstance({ url, label, enablePlugins, disableUI, disableWindowAnimation })`, with all options optional, and returns a numeric managed-player ID, or `false` when the URL fails permission checks. Global code sends with `global.postMessage(numericId, name, data)`; main code sends with `global.postMessage(name, data)`. Both register `global.onMessage(name, callback)`.

The global callback receives `(data, internalPlayerLabel)`. This internal label differs from the custom label returned by main-instance `global.getLabel()`. Critically, string-target sends search `PlayerCore.playerCores`, while managed players are held separately by the plugin controller. Keep the numeric creation result for messages to managed players. The null-target implementation broadcasts to the controller's managed children. Main code can use its custom label to restrict playback setup to the intended managed role. [Pinned global bridge](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptAPIGlobal.swift)

There is no exported `mpv.observeProperty`. Use `event.on("mpv.time-pos.changed", callback)` and `event.on("mpv.pause.changed", callback)`. The changed callback receives the property value. Generic events such as `mpv.file-loaded` and `mpv.end-file` receive **no event data**, so the latter gives no EOF, stop, or error reason. `event.off(eventName, listenerId)` removes the listener returned by `event.on`. [Event bridge](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptAPIEvent.swift), [generic event emission](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/MPVController.swift#L1242-L1246)

`core.status` exposes `paused`, `idle`, `position`, `duration`, `speed`, `videoWidth`, `videoHeight`, `isNetworkResource`, `url`, and `title`. Position, duration, dimensions, and URL can be null at runtime. `core.subtitle.loadTrack(urlString)` checks permissions and loads an external subtitle; it returns no promise. `core.getVersion()` returns `{ iina, build, mpv }`. These APIs belong to the main entry. [Pinned core implementation](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptAPICore.swift)

Both `keep-open` and `keep-open-pause` are safe mpv options, so `mpv.set("keep-open", "yes")` requires no `file-system` permission. With one playlist item, mpv keeps the file at EOF; `eof-reached` then persists for polling through `mpv.getFlag("eof-reached")`. Without keep-open, that flag is cleared immediately as playback unloads. With multiple playlist items, `yes` applies only to the last item; `always` also prevents advancing between items. [Safe options](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/AppData.swift#L274), [mpv keep-open semantics](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/options.rst#L3358-L3396), [EOF property](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/input.rst#L2605-L2610)

Do not depend on `mpv.eof-reached.changed` as the sole completion signal. IINA auto-observes properties outside its fixed table using `MPV_FORMAT_DOUBLE`; the table omits `eof-reached`. mpv's conversion function supports integer/double conversion but no flag/double conversion. Poll the correctly typed getter while keep-open is active, with a guard against completing the same playback twice. Runtime verification is still required. [Observation default](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/MPVController.swift#L826-L828), [property registration](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptAPIEvent.swift#L35-L37), [mpv format conversion](https://github.com/mpv-player/mpv/blob/v0.41.0/player/client.c#L995-L1015)

`mpv.addHook("on_load_fail", 0, () => { /* record opening failure */ })` has no permission gate. A synchronous callback continues automatically and should not call its supplied `next` function. An `async` callback must call `next()` even on failure. The hook identifies opening/demux failure, not every later playback failure; registering it does not require permission to rewrite `stream-open-filename`. [Hook export](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptAPIMpv.swift#L88-L91), [callback continuation](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/MPVController.swift#L62-L77), [load-failure ordering](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/input.rst#L1923-L1931)

The loader resolves `require("./module.js")` relative to the source file currently being evaluated, with an exact filename and extension. Required files use `module.exports`; there is no `exports` alias or Node package resolution. Load modules synchronously from the entry or another module: deferred callbacks have no current source file for the native loader to resolve against. Its cache also checks the supplied path but stores the absolute path, so repeated relative imports must not be used as a shared-state guarantee. IINA installs no `URL` or `URLSearchParams` host polyfill; these browser APIs must not be assumed in host scripts. [Loader](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptPolyfill.swift#L73-L112), [module evaluation and JS context](https://github.com/iina/iina/blob/fbcff4df7183b335880396af0655f6bb89d46442/iina/JavascriptPluginInstance.swift#L113-L191)


## Native debugging findings, 2026-10-20

The user enabled the development plugin in Settings > Plugins. Installation or linking alone did not enable it. After that, the original module-script views displayed a blank window. A native AppKit/WKWebView harness reproduced failed loading of `ui/window/index.js`; ordered classic scripts rendered correctly in both IINA loading modes. `scripts/check-webview.swift --search` also verifies rendered results and pagination after editing the search field.

The user's first decoded-stream attempt crashed before a video window appeared. Its main-thread stack began with `WTFCrashWithInfoImpl`, `WTF::StringImpl::~StringImpl`, and `JSC::SymbolTable::destroy`. A temporary plugin using only public HTTP and a generated local clip reproduced that signature. A minimal child handler narrowed the failure to the synchronous command/acknowledgement path. Deferring only the child reply advanced the handshake but stalled on the next recursive parent-to-child command. Deferring both directions allowed the actual controller and player to reach file loading, sidebar display, progress, and real EOF.

IINA's [global messaging implementation](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIGlobal.swift) and [message hub](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptMessageHub.swift) call the receiving JavaScript context inline. The plugin now schedules outgoing messages in both directions on separate main-loop turns. This is a demonstrated workaround for the tested runtime, not a diagnosis of a general JavaScriptCore defect.

There is a separate scheduling boundary. IINA's HTTP API resolves promises inline from Just's async completion. Pinned [Just source](https://github.com/dduan/Just/blob/1824bf84cf52d11d69ae20cfb89f0ce5bffa5650/Sources/Just/Just.swift) uses URLSession's default serial delegate queue; it does not dispatch completion to main. [Player creation](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptAPIGlobal.swift) constructs controllers inline. The plugin therefore creates the player in a direct [native timer callback](https://github.com/iina/iina/blob/v1.5.0/iina/JavascriptPolyfill.swift), which runs on main. JavaScriptCore itself supports threaded access with VM serialization; do not generalize this into a main-thread-only JavaScript rule.

The maintained `python3 scripts/check-iina-runtime.py` harness exercises the real controller/player with native HTTP completion, messaging, sidebar, timers, and EOF. It substitutes public metadata and a generated private local clip. It neither reads account data nor tests subscriber media availability. Its temporary plugin identity, process-local enable flags, process, and symlink are isolated from the ordinary plugin and cleaned up afterward.
